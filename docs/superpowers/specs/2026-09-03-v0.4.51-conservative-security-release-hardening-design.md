# ShellPilot v0.4.51 保守安全与发布加固设计

> 本轮以“不改变既有 SSH/SFTP/终端行为”为最高约束，只处理已证实的依赖、发布门禁、CI 覆盖与提示文案问题。

## 背景

v0.4.50 已修复 SFTP 双击目录向终端追加提示符、`hik` 切换到 root 后文件身份不可用等问题。最新自检中，4433 项单元测试、生产构建、发布包启动和双更新源字节校验均通过，但仍确认以下风险：

- Windows 安装包与主程序没有 Authenticode 签名。
- Electron 41.2.0 落入已公开安全公告影响范围，且 Electron 41 已停止支持。
- Windows CI 会跳过 Linux/root 文件协议语义测试。
- 部分核心提示绕过运行时翻译，中文与英文界面会混入另一种语言。
- 本地打包缺少 Yarn 时，自动清理命令失败但准备脚本仍可能继续。

## 目标

1. 在 Electron 41.x 内升级到经过当前审计建议修复的 41.10.7，不跨主版本。
2. 将锁文件中的 `qs` 升级到 6.16.0 或更高的兼容 6.x 版本，不改变 Express 配置。
3. 稳定版发布必须提供签名凭据，并在上传前验证安装包和主程序的 Authenticode 状态为 `Valid`。
4. 在 Ubuntu CI 中以 root 身份执行现有特权文件协议测试，覆盖 Windows 环境必然跳过的 Linux 文件系统语义。
5. 将已确认的 SFTP、终端拖放/传输和更新提示接入现有中英文运行时翻译体系。
6. Yarn 自动清理失败必须让打包准备命令失败，并给出可操作错误。
7. 使用现有 Playwright/Electron 场景验证界面和 SFTP 行为，不新增或重排功能入口。

## 非目标与硬边界

- 不修改 SFTP 有效身份探测、目录缓存、受控 PTY、root 文件后端、提示符隐藏或恢复事务逻辑。
- 不改变 SSH 登录、终端输入、SFTP 双击、上传下载、回滚及更新交互流程。
- 不升级到 Electron 42、43、44 或其他主版本。
- 不进行 UI 重设计、布局调整、入口增删、改名或排序。
- 不为拿不到证书的环境生成自签名证书，也不把证书或密码提交到仓库。
- 不在本轮优化前端分块或安装包体积；该工作需要独立性能基线和设计。
- 不自动合并、推送、打标签或发布。

## 方案设计

### 1. 依赖修补

`package.json` 将 Electron 从精确版本 41.2.0 调整为精确版本 41.10.7，保持当前主版本、构建方式和 Electron API 边界不变。`package-lock.json` 通过 npm 的正常解析将 Express/Body Parser 共用的 `qs` 固定到安全兼容版本；不添加业务代码中的直接 `qs` 依赖。

新增依赖安全基线测试，直接读取 `package.json` 和 `package-lock.json`，验证：

- Electron 版本不低于 41.10.7 且仍小于 42.0.0。
- 所有锁定的 `qs` 实例均不低于 6.16.0 且仍处于 6.x。
- Electron 仍为精确版本，避免一次安装自动漂移到未经验证的运行时。

升级后必须重建原生模块，并执行完整单元测试、生产构建和打包启动冒烟。任何 Electron API、node-pty 或窗口行为回归都会阻止继续。

### 2. 稳定版签名与发布门禁

Windows 发布工作流把 GitHub Secrets `WINDOWS_CSC_LINK` 与 `WINDOWS_CSC_KEY_PASSWORD` 映射为 electron-builder 标准环境变量 `CSC_LINK` 与 `CSC_KEY_PASSWORD`。稳定版构建在开始前只检查凭据是否存在，不输出内容；缺失时立即失败。Beta 或本地开发仍可生成未签名包，但不会满足稳定版发布门禁。

新增独立 Authenticode 验证脚本：

- 仅在 Windows 上调用无交互 PowerShell `Get-AuthenticodeSignature`。
- 接收明确的文件列表，不扫描宽泛目录。
- 要求每个目标存在，且签名状态严格为 `Valid`。
- 输出文件名、状态和签名者摘要，不输出证书私钥信息。
- 任一文件缺失、无签名、签名无效或验证命令失败时返回非零退出码。

稳定版工作流在 NSIS 构建完成后验证安装包与 `win-unpacked/ShellPilot.exe`，验证通过后才允许准备、上传发布资产。单元测试通过依赖注入模拟 PowerShell 结果，不依赖开发机证书。

### 3. Linux 特权文件协议 CI

在现有 CI 工作流中增加独立 Ubuntu 作业，不改变 Windows 作业。该作业：

1. 使用与现有 CI 相同的 Node 22 和 `npm ci`。
2. 明确断言运行平台为 Linux。
3. 通过 `sudo` 调用当前 Node 可执行文件，以 UID 0 运行 `test/unit-ci/privileged-file-protocol.spec.js`。
4. 保留测试自身对不可用扩展元数据能力的显式跳过，但不允许因“不是 Linux”或“不是 root”而跳过安全竞态用例。

新增一个小型环境前置校验脚本，并为平台、UID 与命令参数生成编写单元测试。工作流只调用该脚本，避免在 YAML 中复制复杂 shell 判断。

### 4. 运行时提示翻译

沿用现有 `shellpilot-i18n-overrides` 和 `e()/formatShellPilotTranslation()` 模式，只替换本次审计已经定位的字面量：

- SFTP 未选择目标、备份不确定、恢复成功/失败和无恢复记录。
- 终端不安全文件名、传输任务已在进行。
- 更新检查中、下载完成、检查失败和在线更新失败。

每条提示提供中文和英文，不修改按钮、布局、持续时间、错误分支或操作顺序。测试验证两种语言都有非空文本，并验证核心组件不再包含对应的硬编码字面量。

### 5. 打包命令失败传播

Yarn 自动清理仍保留现有命令和产物布局，但必须检查 ShellJS 返回码。失败时抛出包含“安装 Yarn Classic 1.22.22”提示的错误，并停止后续清理与运行时包校验。

测试覆盖成功返回、非零返回及命令异常，确保失败不会被吞掉。官方发布工作流继续显式安装 Yarn Classic；本地缺失 Yarn 时得到明确失败，而不是假成功。

## 数据流与失败处理

- 依赖版本：`package.json/package-lock.json` → 基线测试 → `npm ci` → 原生模块构建 → 完整回归。
- 稳定版签名：GitHub Secrets → electron-builder → 明确目标文件 → Authenticode 验证 → 发布资产准备。凭据和签名任一环节失败都会在上传前停止。
- Linux 门禁：Ubuntu runner → 安装依赖 → root 环境前置验证 → 单文件安全套件。Windows CI 继续独立运行完整单元套件。
- 翻译：组件错误分支 → 稳定翻译键 → 当前预览/保存语言 → Ant Design 消息，不改变原错误对象和恢复记录。
- 打包：Yarn 命令 → 返回码检查 → 成功后继续；失败时立即退出并保留可诊断日志。

## 测试与验收

实施严格按红—绿—重构执行，每个行为先加入失败测试并观察预期失败。

最低验收矩阵：

1. 新增依赖、签名、Linux 前置校验、翻译和打包失败传播单元测试。
2. `npm run test-unit-ci`：0 失败；Windows 平台允许既有的 Linux 条件跳过。
3. `npm run lint`：0 错误。
4. `npm run vite-build`：成功，且不引入新的构建警告类别。
5. `npm run b`：在安装 Yarn Classic 后成功；主动隐藏 Yarn 时必须明确失败。
6. `npm run package:win:dir` 与 `npm run test-package-smoke`：成功。
7. Playwright/Electron 现有 SFTP、终端和核心界面测试通过；重点确认目录双击不追加提示符、`hik → su → root → exit` 身份切换及中英文消息。
8. `npm audit --omit=dev`：不再报告当前 `qs` 公告。
9. `npm audit`：Electron 直接高危项消失；若构建链仍有与运行时无关的公告，必须逐项记录且不得误报为已解决。
10. 稳定版签名脚本对未签名 fixture 失败、对模拟 `Valid` 结果成功；没有真实证书时不声称生成了已签名发布包。

## 提交与回退

每个主题独立提交：规格、依赖、签名门禁、Linux CI、翻译、打包失败传播。若任一主题引发不可接受回归，可单独回退，不影响 v0.4.50 已修复的 SFTP/终端逻辑。

最终只保留可审查分支，不自动合并或发布。真实签名证书和 GitHub Secrets 配置属于外部发布条件，完成代码门禁不等于完成真实签名。
