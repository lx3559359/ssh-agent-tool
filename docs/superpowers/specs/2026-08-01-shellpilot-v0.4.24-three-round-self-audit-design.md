# ShellPilot v0.4.24 三轮用户自检与优化设计

- 日期：2026-08-01
- 审计基线：`origin/master` 提交 `28bfc97`，应用版本 `0.4.24`
- 工作分支：`codex/self-audit-0.4.24`
- 目标：以真实用户视角验证当前版本是否兑现既有需求，连续执行三轮自检，复现并修复当前功能范围内的缺陷、易用性问题和不合理行为。

## 1. 背景与基线

当前远端主线已经合并 Aurora Lift UI，并将应用版本更新到 `0.4.24`。仓库根目录的旧 `master` 落后远端且包含用户未提交改动，因此本轮工作只在从最新远端主线建立的隔离分支中进行。

审计前完整单元基线为：

- `3071` 项测试；
- `3065` 项通过；
- `0` 项失败；
- `6` 项因运行环境跳过；
- 总用时约 `301856 ms`。

依赖安装阶段报告 `8` 个高危依赖告警。该数字只作为审计输入，不直接证明应用存在可利用漏洞，也不授权破坏性依赖升级；第二轮需要检查具体依赖链、实际调用面和兼容修复路径。

## 2. 审计依据与需求优先级

“之前提到的要求”按以下材料建立可追溯需求矩阵：

1. 本轮用户目标与后续明确补充；
2. 当前版本用户指南和 `v0.4.24` 发布说明；
3. `docs/superpowers/specs` 与 `apps/electerm-agent/docs/superpowers/specs` 中当前主线保留的设计规格；
4. 已完成实施计划中的可验证交付项；
5. 当前自动化测试、运行时行为和发布门禁。

发生冲突时，较新的明确产品规格优先于旧规格；用户可见行为以用户指南和最新发布承诺为最低兑现边界；安全约束不得被视觉或易用性目标覆盖。实施计划中的勾选状态只代表历史记录，不能替代当前运行证据。

需求矩阵至少包含以下字段：

| 字段 | 含义 |
| --- | --- |
| ID | 稳定的审计编号 |
| 来源 | 文件、章节、发布条目或用户要求 |
| 要求 | 单一、可验证的行为陈述 |
| 风险 | P0、P1、P2 或 P3 |
| 证据 | 代码、自动化测试、实际操作、截图、日志或构建产物 |
| 状态 | 已满足、部分满足、未满足、无法验证或已废止 |
| 缺口 | 复现步骤、根因和影响 |
| 处置 | 回归测试、修复提交或保留理由 |

“存在测试”不自动等于“已满足”。只有测试确实覆盖对应要求，并且当前版本运行通过时，才可作为有效证据。无法从本地环境验证的真实外部链路必须标记“无法验证”，并记录缺失条件，不得推断为通过。

## 3. 方案选择

采用风险分层的三轮审计。

未采用逐文档串行审计，因为同一用户旅程会在多个历史规格中重复，容易造成大量重复操作而忽略跨模块状态。未采用纯 UI 巡检，因为它无法证明 SSH、SFTP、安全事务、Agent、更新和恢复契约。选定方案以用户旅程组织操作，同时通过需求矩阵保证历史要求不遗漏。

三轮不是重复执行同一测试。每轮使用不同问题模型，并在上一轮修复后的最新状态上重新开始：

1. 第一轮回答“承诺的功能是否存在并能完成主要任务”；
2. 第二轮回答“错误、断线、取消、危险操作和恢复是否诚实且安全”；
3. 第三轮回答“功能是否易懂、一致、响应合理，并具备发布质量”。

## 4. 用户角色与测试数据

以三类普通用户视角操作：

- 新用户：首次启动、未配置服务器和 AI，依赖界面文案理解产品；
- 日常运维用户：保存服务器、连接 SSH、传输文件、查看状态、使用快捷命令和 AI 辅助；
- 故障处理用户：面对认证失败、网络断开、任务超时、传输中断、操作失败和应用重启，需要明确状态与恢复入口。

测试配置使用隔离的 Electron `userData` 目录，不读取或覆盖日常用户配置。测试数据覆盖空状态、少量真实数据、长列表、长日志、中文和英文、浅色和深色主题。

## 5. 第一轮：需求符合性与核心旅程

### 5.1 目标

建立完整需求矩阵，验证当前版本从启动到完成日常任务的主路径，并识别“文档已承诺但界面不可达”“入口存在但流程无法完成”“界面显示成功但后台未完成”等缺口。

### 5.2 用户旅程

1. 首次启动、未连接主页、帮助、设置、语言与主题。
2. 新建连接、快速连接、保存连接、分组、搜索、编辑、移动和删除。
3. 主机指纹确认、密码或密钥认证、连接、重连、标签与窗口操作。
4. 终端输入、搜索、复制粘贴、日志保存、快捷命令和连接信息。
5. SFTP 导航、选择、预览、上传、下载、重命名、覆盖提示、队列与进度。
6. 服务器状态、Fleet 状态、服务发现、只读诊断和 AI 交接。
7. 模型 API 配置、测试、拉取模型、普通对话、上下文引用和停止。
8. 成果物创建、预览、编辑、版本、导出、打开、上传和删除。
9. 故障候选、正式档案、时间线、导出、复盘成果和删除。
10. 运维工具、安全中心、SSH 隧道、更新中心、日志和崩溃恢复入口。

### 5.3 证据

每条主旅程至少保留：操作步骤、预期结果、实际结果、自动化覆盖、必要截图和控制台/主进程错误。对于无法在无凭据环境完成的链路，必须验证其前置检查和错误提示。

## 6. 第二轮：边界、安全与恢复

### 6.1 输入和并发

- 空值、超长值、非法端口、非法路径、重复名称、特殊字符和不同编码；
- 快速双击、重复提交、并发刷新、切换标签、关闭弹窗和组件卸载；
- 大文件、长日志、压缩包、Office 文件、无路径浏览器文件和不匹配 MIME；
- 传输同名冲突、部分文件、空间不足、暂停、继续、取消和重启后续传。

### 6.2 网络和生命周期

- 不可达主机、认证失败、主机指纹变化、SSH/SFTP 中途断线和重连；
- 模型超时、流式中断、空响应、重复响应、配置切换和陈旧响应；
- Agent 与运维任务取消、超时、部分完成、状态未知和远程停止失败；
- 应用异常退出、恢复快照、孤儿任务、数据库迁移和状态持久化。

### 6.3 安全边界

- 只读操作不得制造修改记录或多余确认；
- 写入、删除、覆盖、服务、网络、防火墙和权限操作必须在执行前显示真实目标、命令或差异、备份与回滚信息；
- 取消不得伪装为回滚或远端成功；
- API Key、密码、私钥、认证头和敏感路径不得进入聊天历史、诊断包、导出、错误页或提交差异；
- MCP、CLI、Skill 和 Agent 声明不得绕过系统分类、授权与 endpoint 绑定。

### 6.4 依赖风险

运行生产依赖审计，定位 `8` 个高危告警的直接依赖、传递路径、修复版本和实际可达调用面。只接受当前主版本内、经过 Office/压缩/构建回归验证的窄修复；若只能通过不兼容强制升级清除数字，则记录风险，不执行 `npm audit fix --force`。

## 7. 第三轮：易用性、一致性、性能与发布质量

### 7.1 易用性

- 首次使用时，核心入口、前置条件和下一步是否清楚；
- 空状态、加载状态、成功、失败、取消和部分完成是否易于区分；
- 错误是否包含原因、影响、可执行下一步和稳定错误编号；
- 危险操作按钮层级是否合理，默认焦点是否安全；
- 同一概念在顶部栏、侧栏、设置、日志和帮助中的命名是否一致；
- 中文和英文是否完整，技术字段是否避免错误翻译。

### 7.2 Aurora 与可访问性矩阵

实际启动应用检查：

- 1366×768 与 1920×1080；
- Windows 100%、125% 和 150% 缩放；
- 浅色和深色主题；
- 中文和英文；
- AI 面板开关、侧栏开关、终端/SFTP 分栏和主要弹窗；
- 键盘 Tab、Enter、Escape、焦点环、禁用态、滚动和减少动态效果。

核验 `v0.4.24` 的 Aurora 发布承诺：容器层级明显、圆角语义一致、深色模式可辨、普通数据行保持平面、无裁切/溢出/焦点丢失，且没有改变 SSH、SFTP、终端、AI、路由、数据或快捷键行为。

### 7.3 性能与容量

检查冷启动、主页可交互、打开设置、首个 AI 流式事件、只读 Agent 调用、长历史滚动、Fleet 刷新、SFTP 大文件进度和取消收口。使用现有阈值和性能测试，不因失败而放宽门槛；波动必须用多次样本或明确环境证据解释。

### 7.4 发布质量

最终运行 lint、完整单元测试、关键 Electron E2E、生产构建、打包运行时验证、Windows 便携包检查、生产依赖审计和在线更新源验证。审计分支不上传发布资产、不修改线上更新源、不创建正式发布。

## 8. 缺陷处理闭环

每个确认问题独立执行以下流程：

1. 记录用户可观察的症状和稳定复现步骤；
2. 收集错误、日志、调用链、最近改动和相邻正常实现；
3. 明确单一根因假设并做最小验证；
4. 先写最小回归测试并确认它因该缺陷正确失败；
5. 实施只处理根因的最小修复；
6. 运行聚焦测试并确认通过；
7. 运行相邻模块与完整回归；
8. 按原用户步骤实际复测，并更新需求矩阵和轮次报告。

一次不得混合多个根因。若同一问题连续三次修复假设失败，应停止补丁叠加，重新评估架构并记录决策。

## 9. 严重级别与处置规则

| 级别 | 定义 | 本轮要求 |
| --- | --- | --- |
| P0 | 数据丢失、凭据泄漏、未授权远程修改、应用主流程完全不可用 | 立即停止相关测试，修复并全量回归 |
| P1 | 核心功能不可完成、状态撒谎、无法恢复、严重安全或兼容问题 | 本轮必须修复 |
| P2 | 有绕行方案的功能缺陷、明显易用性问题、重要视觉或性能回归 | 当前功能范围内修复 |
| P3 | 低影响文案、间距、一致性或轻量优化 | 风险低且不扩大范围时修复，否则记录 |

不得为了让报告“零问题”而降低级别、删除失败用例或把真实缺陷改写成预期行为。

## 10. 真实外部链路安全边界

- 真实 SSH 默认只运行 `uname`、`id`、`pwd`、状态读取和有界日志查询；
- 真实 SFTP 写入仅允许位于随机的 `/tmp/.shellpilot-audit-<id>` 隔离目录，完成后必须验证清理；
- 不修改真实服务、账号、防火墙、网络、计划任务、系统配置或生产文件；
- 真实模型调用只发送无敏感信息的短提示，并只保存有界、脱敏结果；
- 不在输出、日志、截图、提交或报告中记录 API Key、密码、私钥、Authorization、Cookie 或 VPS 凭据；
- 在线更新只做检查与验证，不发布、不覆盖历史版本。

## 12. 错误处理与停止条件

- 发现潜在远程写入、凭据泄漏或数据破坏时，立即停止该路径并保存脱敏证据；
- 无法稳定复现时先增加观测，不猜测修复；
- 外部服务不可用时验证本地错误收口并记录外部证据，不把它标为产品通过或产品失败；
- 基线测试、构建或运行环境失败时先区分环境问题与产品问题；
- 临时文件、测试进程、Electron 用户数据和远端隔离目录必须在每轮结束时清理。

## 13. 完成标准

只有以下条件全部满足，三轮审计才可完成：

1. 全部需求来源已进入矩阵，每条都有当前状态与足够证据；
2. 三轮均有独立操作记录，且后一轮基于前一轮修复后的版本执行；
3. 所有确认缺陷都有严重级别、根因、红—绿回归证据和实际复测结果；
4. P0、P1 无遗留，当前范围内的 P2 已修复；未处理 P3 有明确理由；
5. 当前版本对用户指南和 `v0.4.24` 发布承诺不存在未说明的“部分满足”或“未满足”；
6. 完整单元测试、lint、生产构建、关键 E2E 与运行时验证为零失败；
7. 真实模型、真实 SSH/SFTP 或其无法验证原因均有脱敏记录，远端临时目录已清理；
8. 最终差异只包含与确认缺陷、必要测试和审计文档相关的改动；
9. `git diff --check` 通过，最终差异和提交历史经过独立审查；
10. 没有凭据、隐私数据、生成安装包、临时配置或审计用户数据进入提交。

## 14. 非目标

- 新增产品形态、模型协议、远程权限或无人确认的自动运维；
- 为审计方便重写架构或大规模重排信息结构；
- 改变已经确认的 Aurora 视觉方向；
- 使用破坏性依赖升级只为清除审计数字；
- 发布 `v0.4.25`、推送更新资产或修改线上发布状态。
