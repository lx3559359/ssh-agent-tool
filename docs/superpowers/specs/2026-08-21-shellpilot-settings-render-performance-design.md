# ShellPilot 设置页渲染性能优化设计

## 状态

- 日期：2026-08-21；2026-08-22 根据真实性能数据修订
- 状态：实现和三轮核心性能验证完成，进入全量验证与发布
- 范围：客户端设置抽屉的首次打开、重复打开和稳定帧耗时

## 背景与证据

当前性能端到端基线显示，AI 输入和侧栏切换已经满足现有预算，但设置页仍是最明显的交互卡顿点：

- AI 输入延迟：P50 24.70ms，P95 27.20ms，最大值 30.10ms。
- AI 面板打开：总耗时 101.4ms。
- 右侧面板切换：总耗时 95.4ms。
- 设置页首次打开：总耗时 378.7ms，其中可见阶段 97.7ms，稳定帧阶段 280.2ms。

设置抽屉本身没有进入动画。`setting-common.jsx` 在挂载后通过零延时任务将 `ready` 置为真，随后一次性同步渲染四个大型设置区块。抽屉约 98ms 后已经可见，但主线程又被同步渲染、样式计算和布局工作占用约 280ms，因此稳定帧迟到。现有设置区块也没有使用渲染隔离，而项目中的 AI 历史记录已经验证了 `content-visibility` 与固有尺寸占位的可用模式。

这些证据将本轮根因范围收敛到设置内容的一次性挂载和离屏布局成本，而不是抽屉动画、AI 输入路径或全局状态复制。

## 目标与性能预算

在不改变设置功能和用户可见行为的前提下，达到以下预算：

- 冷启动后第一次打开设置：总耗时不超过 250ms。
- 同一客户端会话内重复打开 10 次：总耗时 P95 不超过 150ms。
- 每次打开从内容可见到连续两个稳定帧：不超过 100ms。
- 打开测量窗口内不出现超过 100ms 的 Long Task；不支持 Long Task API 的运行环境以总耗时和稳定帧预算为准。
- AI 输入、AI 面板打开和右侧面板切换不得比本轮修改前的预算退化。

冷打开定义为应用启动完成后的第一次设置页打开。重复打开样本在同一会话内完成，每次关闭后等待连续两个稳定帧再开始下一次打开。P95 使用 10 个重复打开样本计算。

## 用户行为约束

优化后必须保持以下行为不变：

- 设置抽屉标题、关闭入口、搜索和首屏设置立即可用。
- 启动与连接、网络与更新、界面与语言、高级设置四个区块完整存在。
- 搜索可以命中任一区块中的设置项，并将命中内容及时渲染出来。
- 用户可以滚动到高级设置，键盘焦点顺序和焦点陷阱保持正确。
- 关闭再打开设置时，现有状态保留规则不变。
- 设置项的读取、保存、副作用和错误提示逻辑不变。

## 非目标

- 不重写全局状态容器、`main` 组件或通用深拷贝逻辑。
- 不改变设置的信息架构、文案、数据格式或后端接口。
- 不通过删除、隐藏或永久延迟设置项来换取指标。
- 不在本轮重构 SSH、SFTP、AI 对话或终端渲染链路。
- 不以预加载设置模块作为主要方案；预加载只能减少约 98ms 的可见阶段，无法直接解决 280ms 的稳定帧阻塞。

## 方案选择

采用“先隔离、后分帧”的两阶段策略。

### 第一阶段：渲染与布局隔离

为每个 `SettingSection` 建立可复用的渲染边界：

- 在设置区块根节点使用 `content-visibility: auto`，跳过视口外区块的首次绘制和布局。
- 使用 `contain-intrinsic-size` 提供稳定的离屏占位，避免滚动条高度和滚动位置在区块实际渲染后明显跳变。
- 使用只覆盖设置区块所需范围的 containment，不隔离抽屉头部、搜索框或焦点管理节点。
- 为不同规模的区块提供稳定的区块类名或尺寸变量，避免所有区块共享明显错误的估算高度。

第一阶段改动局部、浏览器原生调度成本低，也是项目内已有的性能模式。若第一阶段已经满足全部预算，本轮不引入额外的挂载状态机。

### 第二阶段：视口驱动的按需挂载

第一阶段真实性能端到端测试仍超出核心预算，因此启用按需挂载：

- 抽屉头部、搜索和第一个可见设置区块在首次提交中同步挂载。
- 其余区块保留稳定占位，不在打开测量窗口内无条件后台挂载。
- `IntersectionObserver` 以设置内容滚动容器为根；区块进入视口或预加载边界时才请求挂载。
- 同一帧出现多个请求时，使用可取消的 `requestAnimationFrame` 队列，每帧至多挂载一个大型区块。
- 未挂载区块保留固有尺寸占位，避免滚动范围突然变化。
- 打开完成定义为抽屉、首个设置区块以及当前视口内区块可用，并经过连续两个稳定帧；离屏区块不属于打开完成条件。
- 用户滚动到未挂载区块时，目标区块在下一动画帧挂载；滚动容器中的占位仍保持文档顺序。
- 首个启动区块立即提供一个可交互的快捷键控件；启动会话和两个数值设置保留等高占位，在组件挂载 160ms 后按动画帧分成两组补齐，避免第二次大型提交进入打开门禁。
- 不支持 `IntersectionObserver` 时，在首屏稳定后按动画帧逐个挂载其余区块，保持功能完整。
- 组件卸载或抽屉关闭时取消观察器和未执行回调，禁止卸载后更新状态。
- 分帧只改变呈现时机，不改变设置数据初始化、事件处理和保存逻辑。

第二阶段的启用门槛是：第一阶段完成后，冷打开大于 250ms、重复打开 P95 大于 150ms、稳定帧大于 100ms，或出现超过 100ms 的 Long Task。只要任一条件成立就实施第二阶段并重新测量。

## 组件边界

- `setting-common.jsx`：保留设置数据和交互编排；若需要第二阶段，则负责区块清单、挂载优先级和调度生命周期。
- `setting-section.jsx`：提供区块级稳定类名、可选尺寸提示和占位边界，不持有设置业务状态。
- `setting.styl`：实现 `content-visibility`、固有尺寸与必要的 containment 样式。
- `client-interaction-performance.js`：扩展设置页测量，记录冷打开、重复打开样本、可见阶段、稳定帧和 Long Task。
- 性能端到端用例：执行真实打开、关闭、重复打开和功能回归，并作为预算门禁。

业务设置组件不感知性能测量逻辑，性能辅助代码也不修改产品运行状态。

## 性能测量设计

每次设置打开记录以下时间点：

1. 用户动作开始。
2. 设置抽屉目标节点可见。
3. 首个设置区块以及当前视口内区块可用后的第一个动画帧。
4. 上述条件满足后的第二个连续动画帧。

由此输出动作到可见、可见到稳定帧和总耗时。测量开始前注册 `PerformanceObserver` 监听 `longtask`，在第二个稳定帧后停止监听，仅统计与本次打开窗口重叠的条目。输出每次 Long Task 的开始时间和持续时间，以及窗口内最大值。

重复打开测试在冷打开完成后执行 10 轮。每轮先确认抽屉完全关闭并经过两个稳定帧，防止关闭阶段工作污染下一轮样本。P95 使用最近秩方法计算：对 10 个样本升序排列后取第 10 个样本，因此当前门禁实质上要求 10 次重复打开全部不超过 150ms，避免少量明显卡顿被平均值隐藏。

若运行环境不支持 `PerformanceObserver` 或 `longtask` 类型，测试明确记录“不支持”，但仍执行并强制总耗时和稳定帧门禁。

## 测试驱动实施顺序

1. 先扩展性能端到端测试，将设置页冷打开预算收紧到 250ms，并加入稳定帧 100ms、重复打开 P95 150ms 和 Long Task 100ms 门禁。当前 378.7ms/280.2ms 基线应使新门禁失败。
2. 加入设置页功能回归断言：首屏区块立即存在；依次滚动到其余三个占位后，区块及代表性设置项及时挂载；搜索、键盘焦点和关闭重开可用。
3. 实施第一阶段渲染隔离，运行性能测试并记录新数据。
4. 若第一阶段满足全部预算，停止增加复杂度；若未满足门槛，则先为可取消分帧调度器添加单元测试，再实施第二阶段。
5. 若按文档顺序自动逐帧挂载仍使稳定帧超时，则停止后台全量挂载，改为视口驱动的逐区块请求，再重新测量。
6. 对最终方案执行相关单元测试、性能端到端测试、完整客户端测试、代码检查和生产构建。

分帧调度器的单元测试至少覆盖请求去重、每帧上限、独立区块请求和关闭时取消。

## 错误与兼容处理

- 浏览器不支持 `content-visibility` 时，设置页继续完整同步渲染；性能端到端结果决定是否需要第二阶段兜底。
- 固有尺寸估算只用于离屏占位，不写入业务数据，也不阻止浏览器在区块可见时采用真实高度。
- 调度回调在组件卸载后不得调用 `setState` 或继续挂载区块。
- 观察器不可用时使用首屏稳定后的逐帧降级路径，不允许永久隐藏离屏区块。
- 延后挂载的启动区块细节必须在正常停留时自动补齐；占位不得获取焦点，组件关闭时必须取消延迟和队列。
- 搜索输入变化期间不丢弃已输入文本；待渲染目标必须在下一帧可用。
- 任一区块渲染异常继续交由现有错误边界处理，不静默跳过设置项。
- 所有性能日志只包含阶段名称和耗时，不包含设置值、用户路径或凭据。

## 验收标准

- 冷打开、重复打开 P95、稳定帧和 Long Task 指标全部满足目标预算。
- 首屏设置立即可用；其余三个区块在滚动到视口附近后逐个挂载，四个区块、搜索、键盘焦点和关闭再打开通过真实客户端回归。
- AI 输入 P95 保持在 50ms 以内，AI 面板和右侧面板切换保持在 250ms 以内。
- 不新增控制台错误、React 卸载后更新警告、明显滚动跳变或焦点丢失。
- 相关单元测试、性能端到端测试、完整客户端测试、代码检查和生产构建通过。
- 最终性能报告同时列出优化前后数据，并说明是否启用了第二阶段分帧挂载。

## 2026-08-22 实测修订依据

第一阶段仅使用 `content-visibility` 后，冷打开总耗时仍为 391.7ms，稳定帧为 290.3ms，最大 Long Task 为 197ms；因此已达到第二阶段启用门槛。

第二阶段最初按文档顺序自动逐帧挂载全部四个区块。该实验把一次大型提交拆成约 116ms、80ms、153ms 和 68ms 的多次工作，但打开测量仍等待全部区块，导致冷打开总耗时升至 501.6ms、稳定帧升至 391.4ms，重复打开 P95 为 303.4ms。数据证明“后台逐帧挂载全部区块”和“所有区块完成后才算打开”会把离屏工作串行加入关键路径，不能满足本设计目标。

因此修订后的唯一实现方向是：首屏稳定即完成打开，离屏区块只在进入视口或预加载边界时请求挂载。功能门禁仍必须真实滚动并验证四个区块全部可用；性能门禁只统计用户当前可见内容的关键路径。该修订不降低功能完整性，只把不可见工作从打开关键路径移到用户实际访问该区块的时点。

## 2026-08-22 首屏细分与页签导航修订

视口驱动实现把冷打开降到 194.4ms，但冷稳定帧仍在 97.2ms 附近，重复打开 P95 为 167.6ms。受控 A/B 分别移除快捷键、启动会话选择器和数值控件，单项移除都不能稳定满足 150ms；只渲染区块标题时暖 P95 为 147.8ms，证明额外提交与控件组合共同构成剩余成本。把常规设置的 `ready` 二次提交合并到首次提交，并将仅用作导航的 Ant Design `Tabs` 替换为轻量原生 tablist 后，完整启动区块暖 P95 为 147.4ms，但三轮中仍出现 149.3ms 的临界样本和 105.9ms 的冷稳定帧。

最终首屏细分采用以下约束：

- 设置页签只承担导航，不承载 Ant Design 的隐藏内容面板，因此改用原生 `tablist` 和 `button[role=tab]`；保留现有类名、顺序、标签和点击语义，并实现方向键、Home、End、`aria-selected` 与 roving `tabIndex`。
- `SettingCommon` 首次提交不再先显示加载图标再用零延时任务二次提交。
- 启动区块标题和快捷键控件同步可用，性能就绪选择器必须命中该快捷键按钮，而不能只命中空区块外壳。
- 启动会话选择器与两个数值项使用稳定占位；组件挂载 160ms 后进入可取消队列，每个动画帧挂载一组。
- 离屏网络、界面和高级区块仍由视口观察器独立请求；首屏较短时不得因为占位变化提前触发网络区块。

组合实验“轻量页签 + 首次直接提交 + 仅快捷键同步”得到冷打开 171.1ms、冷稳定帧 73.5ms、暖 P95 138.1ms、最大 Long Task 95ms。该结果为最终实现提供了比预算至少约 12ms 的暖打开余量；正式验收仍以删除全部 A/B 开关后的三轮真实性能门禁为准。

## 2026-08-22 最终实现与稳定性结果

删除全部实验开关后的连续压测发现，抽屉关闭时使用 `visibility: hidden` 会让保留的设置树恢复显示时重新绘制，暖打开偶发达到 151.9ms。最终实现保留已打开过的设置树，关闭时改用合成层 `opacity: 0` 和 `pointer-events: none`，再次打开只切换透明度；关闭提交完成后显式设置 `inert` 与 `aria-hidden`，避免 React 对空字符串布尔属性的省略以及背景隔离清理覆盖关闭态属性。这样既阻止隐藏界面交互和聚焦，也避免每次重绘整页抽屉。

后续高负载自检又发现三个边界问题。第一，原生页签替换后缺失旧页签内容容器的 flex 布局契约，抽屉外层承担了滚动，内部观察器无法可靠感知滚动；最终为显式 `tabpanel` 恢复 `display: flex`、伸缩、最小高度和溢出约束，并从当前表单向上解析唯一的 `.setting-col-content`。第二，抽屉可见状态变化会让父组件重新创建整套设置内容 JSX，已挂载树仍被 React 全量对比；最终把可观察的设置内容拆成独立更新边界，并用 `useMemo` 保持开关抽屉时的元素引用稳定。第三，启动会话、数值控件和语言下拉的定时挂载会与快速关闭/重开碰撞；启动细节改为在 `requestIdleCallback` 空闲窗口内直接完成提交，并提供 600ms 超时和卸载取消兜底，避免只排队到下一帧。两个常规数值项与语言选择改用轻量原生控件，保留原保存、预览、应用和取消语义，不再产生后台重控件提交。离屏网络、界面和高级区块只在用户实际滚动后按可见区块逐帧挂载。

最终显隐优化和测试网络隔离完成后，连续三轮完整性能端到端结果如下：

- 第 1 轮：冷打开 143.6ms、冷稳定帧 73.3ms、暖打开 P95 88.0ms、最大 Long Task 81ms、AI 输入 P95 18.1ms。
- 第 2 轮：冷打开 147.6ms、冷稳定帧 79.5ms、暖打开 P95 82.3ms、最大 Long Task 77ms、AI 输入 P95 11.1ms。
- 第 3 轮：冷打开 149.2ms、冷稳定帧 77.6ms、暖打开 P95 81.8ms、最大 Long Task 74ms、AI 输入 P95 14.8ms。

三轮均满足冷打开 250ms、暖打开 P95 150ms、稳定帧 100ms、Long Task 100ms 和 AI 输入 P95 50ms 的预算。功能门禁同时验证了四个设置区块按需挂载、数值设置提交/取消/恢复、搜索跳转、焦点、页签键盘导航、关闭重开、关闭态 DOM 隔离和零渲染器错误。测试模式跳过自动更新外网请求，AI 健康检查使用本地受控服务，确保性能门禁不受网络状态污染；生产更新行为不变。

在最终发布顺序自检中，基础性能用例先运行时曾暴露出另一个残余长任务：真实关闭会清空 `settingItem`，同一通用设置页重开时又写入等价新对象，导致已隐藏的内容树先在关闭时重渲染、再在打开时重渲染。最终关闭路径在当前会话保留选中项，同一通用设置页重开仅改变可见状态；需要销毁表单状态的其他调用仍保留原默认清理语义。修复后按 `029.performance-baseline` 再到 `038.client-interaction-performance` 的完整顺序运行，冷打开 154.5ms、冷稳定帧 79.2ms、暖打开 P95 66.8ms、暖稳定帧最大 65.3ms、暖打开最大 Long Task 54ms、AI 输入 P95 15.3ms，两个性能用例全部通过。
